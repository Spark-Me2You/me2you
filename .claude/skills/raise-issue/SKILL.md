# Raise an issue

Issues here feed an automated agent pipeline (`docs/AGENT_WORKFLOW.md`). The issue body is all a coding agent sees, so write it to stand alone. The repo is public: no secrets, tokens, personal data or private URLs in the issue.

## 1. Pick the route

- **You can write the full spec** (the request is clear, or the user answered your questions): write it in the format below and create the issue. No `spec:request` needed.
- **Only a rough idea** (the user wants it captured, not designed): create the issue in plain language with `--label spec:request`. The `spec.yml` workflow drafts the spec, and a repository owner/admin always reviews it before separately starting the agent. Use this for bulk capture too.

Default to the first when the user is in the session with you. Ask a question only where a real design decision is open and a sensible default would be a guess.

## 2. Write the spec

Read `docs/AGENT_WORKFLOW.md` ("Writing an agent-ready issue"). Look at the code the request touches so the code pointers are real files and patterns. The source of truth for sections is `.github/ISSUE_TEMPLATE/`. Use the template that matches:

| Kind | Template | Sections, in order |
|---|---|---|
| New user-facing feature | `feature.yml` | Area, Problem / motivation, Proposed behaviour, Acceptance criteria, Out of scope, Code pointers |
| Bug | `bug.yml` | Area, What happens, What should happen, Steps to reproduce, Code pointers, How to verify the fix |
| Refactor, style, perf, test, docs, chore | `task.yml` | Area, What needs doing, Acceptance criteria, Code pointers |

Format each section as `### <label>` followed by its content. Add `### Manual verification` when confirming the change needs the kiosk, camera or Pixi.

- **Area:** one comma-separated line using area names: kiosk, hub, discovery, games, cv, mobile, auth, db, ci. Triage reads this line to add `area:*` labels.
- **Acceptance criteria:** a `- [ ]` checklist. Make items checkable with `npm run build` and unit tests where possible.
- **Scope:** one logical change. If the request is several, create several issues and cross-reference them.
- **Don't invent requirements.** Pick the simplest sensible default and state it.
- **Database work** (migrations, RLS, edge functions) is not agent work. Label it `area:db` / `type:db`; the agent refuses it.

## 3. Create it

Title: `<type>: <imperative summary>`, 72 characters max, per `docs/GIT_CONVENTIONS.md`.

Write the body to a file in the scratchpad (or another temp location outside the repo) and create the issue from it, so quoting can't mangle it:

```bash
gh issue create --title "feat: ..." --body-file <path> \
  --label type:feature --label area:games [--label spec:request] [--label model:opus]
```

- Types: feature, fix, refactor, style, docs, chore, db, perf, test (`type:<name>`).
- Add `model:opus` only for hard work; the default is Sonnet. Never add two `model:*` labels.
- Don't add `Closes`/`Fixes` lines, AI attribution or "generated by" footers.

## 4. Don't start the agent unless asked

`agent:ready` starts a run that costs subscription quota and opens a PR. Add it only when the user explicitly asks the agent to do the work, and never to a `spec:request` issue (there's no spec to work from yet). If the user asks, show them the issue first. Only current repository owners/admins can trigger runs; if the label is removed with a comment, report that rather than retrying.

`spec:request` never starts the agent. It always produces `spec:review` (or asks for more input), and a repository owner/admin must review the result and separately add `agent:ready`.

## 5. Report back

Give the issue URL and the next step: for a `spec:request` issue, "wait for `spec:review`, have a repository owner/admin edit or approve the spec, then separately add `agent:ready`"; for a full spec, "a repository owner/admin can add `agent:ready` when the agent should pick it up."
